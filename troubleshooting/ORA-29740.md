# ORA-29740: evicted by instance number, group incarnation

**Applies to:** 11g to 23ai (RAC)

## Cause

LMON evicted this instance from the clustered database to protect data integrity, because it could not confirm cluster membership or health within the allowed time. This is Instance Membership Recovery. The instance normally rejoins automatically once the cluster reconfigures, so by the time anyone investigates, the database is healthy again and the only evidence is in the logs.

An instance eviction, raised as ORA-29740 by LMON, is not the same as a CSS node eviction, which reboots the whole server. The two often occur together, and confusing them wastes time. The reason code in the LMON trace file identifies which layer acted.

Almost every eviction has one of three root causes:

- Interconnect failure. The private network dropped packets or saturated, so the network heartbeat was missed.
- Storage latency. The voting disk heartbeat timed out, usually a shared-storage or multipath stall.
- Node hang. CPU exhaustion or memory swapping meant the heartbeat threads were not scheduled in time, so a live node looked dead.

## Check

This is a forensic exercise. No single log tells the whole story; the diagnosis comes from lining up timestamps across layers.

Confirm the eviction in the alert log and open the LMON trace it names. The reason code and reconfiguration detail are there, not in the alert log:

```sql
SELECT inst_id, value AS diag_trace
FROM   gv$diag_info
WHERE  name = 'Diag Trace'
ORDER  BY inst_id;
```

Check whether Clusterware also evicted or rebooted the node. On 12.2 and later the CRS logs are in ADR at `$ORACLE_BASE/diag/crs/<node>/crs/trace`, with `alert.log` and `ocssd.trc`. Earlier releases use `$GRID_HOME/log/<node>/`. A reboot recorded here means CSS acted at the cluster layer, not just LMON at the database layer.

Confirm which interconnect the database is actually using, then check for lost blocks, the clearest interconnect-health signal:

```sql
SELECT inst_id, name, ip_address
FROM   gv$cluster_interconnects
ORDER  BY inst_id;
```

```sql
SELECT inst_id, value AS gc_blocks_lost
FROM   gv$sysstat
WHERE  name = 'gc blocks lost'
ORDER  BY inst_id;
```

A non-zero and rising `gc blocks lost` means the interconnect is dropping packets, which points at the network as the cause.

Check the voting disks and the heartbeat timeouts, as the Grid owner:

```
crsctl query css votedisk
crsctl get css misscount
crsctl get css disktimeout
```

`misscount` bounds the network heartbeat, default 30 seconds. `disktimeout` bounds the voting disk heartbeat, default 200 seconds. These are the thresholds that were breached.

Look at node health at the moment of eviction with Cluster Health Monitor:

```
oclumon dumpnodeview -allnodes -last "00:15:00"
```

CPU pinned at 100 percent, a long run queue, swap activity, or a device at sustained high IO wait in the seconds before the eviction is what distinguishes a starved node from a network fault. This step is the one that most often settles the diagnosis.

`oclumon` reads Cluster Health Monitor history from the Grid Infrastructure Management Repository. Where the repository is not deployed, which is the case on some Oracle Database Appliance and 19c installations, the command returns `CRS-9118` and `CRS-9121` and no data is available. This does not affect the databases. Confirm with `srvctl status mgmtdb`. When the repository is absent, use OSWatcher archives for the same window, or OS level data such as `top`, `vmstat`, `sar` and `iostat` if OSWatcher is not running, to establish node health at the time of the eviction.

## Fix

The instance has already rejoined. The work is identifying the root cause so it does not recur. Match the evidence to one of the three.

Interconnect:

- Confirm the private interconnect is on a dedicated, non-routed network and that every node agrees on the interface (`oifcfg getif`).
- Check for interface errors, MTU mismatches, and inconsistent jumbo-frame configuration. A switch silently dropping oversized frames produces exactly this pattern and is a common hidden cause.

Caution: change interconnect configuration only through `oifcfg` and the cluster's own procedure. A wrong manual change can stop the whole cluster starting.

Storage:

- Check shared-storage latency to the voting disks around the eviction time. Sustained IO stalls beyond `disktimeout` evict the node.
- Multipath failover events during the window are a frequent trigger. Review the OS multipath and SAN logs for the same timestamp.

Node hang:

- If Cluster Health Monitor or OSWatcher shows CPU saturation or swapping, the node was alive but too starved to heartbeat. Find what consumed it: a runaway job, memory oversubscription, or a backup saturating IO.
- Raising `misscount` to stop the evictions is almost always wrong here. It hides a real resource problem and slows detection of genuine failures.

## Prevent

- Keep OSWatcher and Cluster Health Monitor running with adequate retention. Without them a transient eviction is close to undiagnosable after the fact, and the next one will be too.
- Dedicate and monitor the private interconnect: bandwidth, interface errors, and redundancy through HAIP or a bonded NIC.
- Monitor voting disk IO latency, not only its availability.
- Size memory so the node never swaps. Swapping starves the CSS and LMON threads that must heartbeat, and turns a busy node into an evicted one.
- Do not widen `misscount` or `disktimeout` as a first response. They exist to bound how long the cluster waits before protecting data integrity. Widening them trades faster protection for fewer evictions and masks the real fault.

## Version notes

- 11.2 onwards, HAIP provides interconnect redundancy at the Grid layer. Where a node has more than one private NIC, confirm HAIP is active rather than assuming the redundancy works.
- 12.2 onwards, Clusterware logging moved to ADR under `$ORACLE_BASE/diag/crs/<node>/crs/trace`. On earlier releases the same logs are under `$GRID_HOME/log/<node>/`.
