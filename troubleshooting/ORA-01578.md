# ORA-01578: ORACLE data block corrupted

**Applies to:** 11g - 23ai

## Cause

Oracle read a block whose contents failed its consistency check. The error names the file number and block number. The cause is usually below the database: a failing disk, a storage or firmware fault, or a lost write in the IO path. It can also follow from an incomplete or wrongly handled recovery.

Corruption is physical when the block itself is damaged, or logical when the block is structurally intact but its contents are inconsistent. ORA-01578 is the physical case.

On RAC every instance reads the same shared datafiles, so a corrupt block is visible from all instances. The node that happens to read it first raises the error.

## Check

Identify the object that owns the reported file and block:

```sql
SELECT owner, segment_name, segment_type
FROM   dba_extents
WHERE  file_id = &file_id
AND    &block_id BETWEEN block_id AND block_id + blocks - 1;
```

List blocks Oracle has already flagged as corrupt:

```sql
SELECT * FROM v$database_block_corruption;
```

Run a full physical check with RMAN, which records every corrupt block without stopping at the first:

```sql
RMAN> BACKUP VALIDATE CHECK LOGICAL DATABASE;
```

After it completes, review the findings:

```sql
SELECT file#, block#, blocks, corruption_type
FROM   v$database_block_corruption
ORDER  BY file#, block#;
```

Check the alert log and operating system messages for disk errors around the time the corruption appeared. Physical corruption is a storage symptom, and the root cause is usually recorded there.

## Fix

Where a valid backup and the archived redo since it exist, recover the affected blocks. Block media recovery repairs only the damaged blocks and leaves the datafile online:

```sql
RMAN> RECOVER DATAFILE 7 BLOCK 128;
```

Or recover every block RMAN has recorded as corrupt:

```sql
RMAN> RECOVER CORRUPTION LIST;
```

Caution: recovery requires a backup of the block from before the corruption plus the redo to roll it forward. Without both, block media recovery cannot repair the block.

Where the corrupt block belongs to an index, the simplest repair is to drop and rebuild the index, since the data can be regenerated from the table:

```sql
ALTER INDEX schema.index_name REBUILD ONLINE;
```

Where no backup exists and the block is in a table, the rows in that block are lost. `DBMS_REPAIR` can mark the block corrupt so the table can be scanned around it, after which the surviving rows are salvaged into a new table:

```sql
EXEC DBMS_REPAIR.SKIP_CORRUPT_BLOCKS('SCHEMA', 'TABLE_NAME');
```

Caution: this abandons the data in the corrupt block. Use it only when recovery from backup is not possible.

Once the block is repaired, the storage fault that caused it still has to be found and fixed, or the corruption will recur.

## Prevent

- Set `DB_BLOCK_CHECKSUM` and `DB_BLOCK_CHECKING` so Oracle detects corruption when a block is written rather than much later when it is read.
- Run `RMAN BACKUP VALIDATE CHECK LOGICAL` on a schedule to find corruption early.
- Run Data Guard with `DB_LOST_WRITE_PROTECT`, so lost writes are caught by comparison against the standby.
- Take and test regular backups. Block media recovery is only possible with a good backup and the intervening redo.
- Investigate storage and disk errors in the alert log promptly. They are the warning before corruption appears.

## Version notes

- Block media recovery through `RECOVER ... BLOCK` is available from 10g. From 11g, `RECOVER CORRUPTION LIST` repairs every block in `v$database_block_corruption` in one command.
- `DB_LOST_WRITE_PROTECT` applies from 11g onwards.
