# ORA-12541: TNS: no listener

**Applies to:** 11g - 23ai

## Cause

The client reached the host but nothing was listening on the port it connected to. The network path itself is working, which rules out name resolution and routing.

On RAC there are two listener layers: SCAN listeners, which run on three nodes and hand connections off, and local listeners, which run on every node. Both are managed by Clusterware, not by `lsnrctl`.

A SCAN name resolves to three addresses in round robin. When one SCAN listener is down, roughly one connection in three fails and the rest succeed, so the error presents intermittently.

## Check

SCAN and local listener status, run as the Grid owner:

```bash
srvctl status scan_listener
```

```bash
srvctl status listener
```

Clusterware resource state:

```bash
crsctl status resource -t
```

SCAN name resolution, which must return three addresses:

```bash
nslookup my-scan.example.com
```

Listener status on a single instance system:

```bash
lsnrctl status
```

Address the client is resolving:

```bash
tnsping ORCL
```

The host and port reported here must match what the listener reports.

Processes bound to the listener port:

```bash
netstat -an | grep 1521
```

## Fix

On RAC, start listeners through Clusterware:

```bash
srvctl start scan_listener
```

```bash
srvctl start listener -n node1
```

Starting a RAC listener with `lsnrctl start` bypasses Clusterware. The listener runs but is not managed, so it will not restart or fail over and will not come back after a node reboot.

On a single instance system:

```bash
lsnrctl start
```

Recurring causes:

- Listener not started after a server reboot. On RAC, check that `AUTO_START` is enabled on the resource.
- Port mismatch between `listener.ora` and the client `tnsnames.ora`.
- Listener started from the database home instead of the Grid home on RAC.
- Firewall permitting the host but not the listener port. On RAC the SCAN VIPs must be opened as well as the node VIPs.

Restarting a listener does not disconnect established sessions, which communicate with the server process directly. Only new connections fail during the restart.

## Prevent

- Leave listener startup to Clusterware and verify `AUTO_START` on the SCAN and local listener resources.
- Monitor each of the three SCAN addresses individually. Monitoring the SCAN name alone hides a failed listener behind round robin.
- Run `tnsping` from a remote host on a schedule to detect firewall changes and hung listeners.
- Configure static registration for services that must be reachable while the database is down.
- Keep `tnsnames.ora` under version control and deploy it rather than editing it on each client.
