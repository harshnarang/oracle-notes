# ORA-00257: archiver error, connect internal only until freed

**Applies to:** 11g to 23ai

## Cause

The database is in archivelog mode and cannot write a new archived redo log. Until space is freed, sessions block and new connections are refused, except for `SYSDBA`. The instance is up but effectively unavailable.

The usual reason is a full fast recovery area (FRA). The FRA holds archived logs, and often flashback logs and RMAN backups as well, all counting against one size limit. Less often the archive destination is a filesystem that has filled, or the archiver process is stuck on a failed destination.

On RAC each instance archives its own redo threads. One instance can hang on ORA-00257 while the others keep running, so the FRA usage that matters is the one seen by the affected instance.

## Check

Connect as SYSDBA, which is still permitted:

```sql
sqlplus / as sysdba
```

FRA usage:

```sql
SELECT name,
       ROUND(space_limit/1024/1024/1024, 2)                          AS limit_gb,
       ROUND(space_used/1024/1024/1024, 2)                           AS used_gb,
       ROUND((space_used - space_reclaimable)/space_limit * 100, 1)  AS pct_used
FROM   v$recovery_file_dest;
```

`pct_used` at or near 100 confirms a full FRA.

What is occupying the FRA:

```sql
SELECT file_type,
       ROUND(percent_space_used, 1)        AS pct_used,
       ROUND(percent_space_reclaimable, 1) AS pct_reclaimable,
       number_of_files
FROM   v$flash_recovery_area_usage
ORDER  BY percent_space_used DESC;
```

Archive destination status, in case the target itself has failed rather than filled:

```sql
SELECT dest_id, status, binding, destination, error
FROM   gv$archive_dest
WHERE  status <> 'INACTIVE'
ORDER  BY inst_id, dest_id;
```

A non-empty `error` column points to a destination problem rather than a space problem.

Whether logs are being applied to a standby, which is a common reason archived logs are not being deleted:

```sql
SELECT inst_id, process, status, sequence#
FROM   gv$managed_standby
WHERE  process LIKE 'MRP%'
ORDER  BY inst_id;
```

## Fix

The safe fix is to back up the pending archived logs to tape or disk, which lets RMAN delete them and reclaim the space:

```sql
RMAN> BACKUP ARCHIVELOG ALL DELETE INPUT;
```

Where a backup already exists and the logs are confirmed redundant, delete them through RMAN so the catalog and FRA accounting stay correct:

```sql
RMAN> DELETE ARCHIVELOG ALL COMPLETED BEFORE 'SYSDATE-1';
```

Caution: never delete archived redo logs at the operating system with `rm`. RMAN still believes they exist, the FRA space is not released in the controlfile, the error returns, and any recovery that needs those sequences will fail.

To restore service immediately when a backup cannot be taken right away, raise the FRA limit above the current `space_limit` shown by the first query, so sessions unblock. Set it relative to that limit and to the storage actually available, not as a fixed number:

```sql
-- illustrative; raise above the current space_limit, do not copy the value blindly
ALTER SYSTEM SET db_recovery_file_dest_size = 500G SCOPE=BOTH SID='*';
```

This is a holding action, not a fix. The reason the FRA filled still has to be dealt with, or it fills again against the higher limit.

If the cause is a standby that has stopped applying logs, resolve the gap on the standby. The primary keeps every log the standby has not yet acknowledged, so a stalled standby fills the primary FRA.

## Prevent

- Alert on FRA usage at 80 percent, not on the error at 100 percent.
- Confirm the archivelog backup job runs and succeeds. A silently failing backup is the most common root cause.
- Size the FRA for the real retention requirement, including flashback logs and any RMAN copies it holds.
- Monitor standby apply lag where Data Guard is in use, so a stalled standby is caught before it fills the primary.
- Never mix manual OS file deletion with an FRA. Let RMAN manage the space.

## Version notes

- `db_recovery_file_dest_size` and the FRA views apply from 10g onwards.
- 12c onwards in a CDB the FRA is shared across all PDBs. Usage is a container-level figure, not per PDB.
