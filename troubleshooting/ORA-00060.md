# ORA-00060: deadlock detected while waiting for resource

**Applies to:** 11g - 23ai

## Cause

Two sessions each hold a lock the other is waiting for. Oracle detects the cycle and rolls back one statement to break it. The transaction itself is not rolled back and the instance is unaffected.

On RAC the cycle can span instances. Detection is handled by the LMD process on one node, and the trace file is written only on that node.

## Check

Trace directory on each instance:

```sql
SELECT inst_id, value AS diag_trace
FROM   gv$diag_info
WHERE  name = 'Diag Trace'
ORDER  BY inst_id;
```

The alert log names the trace file. The `Deadlock graph` section in it lists both sessions, both SQL statements and the objects involved. On RAC the alert log of every node must be checked, as the detecting instance is not necessarily the one the application connected to.

Sessions currently blocked, across all instances:

```sql
SELECT   s.inst_id,
         s.sid,
         s.serial#,
         s.username,
         s.blocking_instance,
         s.blocking_session,
         s.event,
         o.object_name,
         s.sql_id
FROM     gv$session s
LEFT     JOIN dba_objects o ON o.object_id = s.row_wait_obj#
WHERE    s.blocking_session IS NOT NULL
ORDER BY s.inst_id, s.sid;
```

`BLOCKING_INSTANCE` identifies the node holding the lock. Without it a blocker on another instance does not appear.

Foreign key constraints with no supporting index:

```sql
SELECT c.table_name, c.constraint_name, cc.column_name
FROM   user_constraints c
JOIN   user_cons_columns cc ON cc.constraint_name = c.constraint_name
WHERE  c.constraint_type = 'R'
AND    NOT EXISTS (SELECT 1
                   FROM   user_ind_columns i
                   WHERE  i.table_name      = cc.table_name
                   AND    i.column_name     = cc.column_name
                   AND    i.column_position = cc.position);
```

## Fix

Oracle has already resolved the deadlock. The application should retry the failed transaction.

To clear a session that is still holding locks:

```sql
ALTER SYSTEM KILL SESSION '&sid,&serial,@&inst_id' IMMEDIATE;
```

Caution: this rolls back the session's uncommitted work. The `@inst_id` component is required when the session is on another instance.

The permanent fix depends on what the deadlock graph shows:

- Unindexed foreign key. Updating or deleting a parent row takes a share lock on the whole child table. Create the index on the child key columns.
- Different table access order between two code paths. Standardise the order in which tables are updated.
- Bitmap index on a table taking concurrent DML. A single row change locks a range of rowids. Replace with a B-tree index.
- Long-running transactions holding locks while waiting on external calls. Shorten the transaction.

## Prevent

- Index foreign key columns on any table whose parent is updated or deleted.
- Use one table access order across all application code.
- Acquire locks as late as possible and commit promptly.
- Handle ORA-00060 in the application with a single retry.
- On RAC, route each application module through its own service so related work stays on one instance. Cross-instance deadlocks take longer to detect and are harder to trace.
- Track deadlock frequency rather than individual occurrences.

## Version notes

- 12.2 onwards the deadlock graph includes the blocking SQL text as well as the SQL ID.
