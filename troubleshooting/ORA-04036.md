# ORA-04036: PGA memory used by the instance exceeds PGA_AGGREGATE_LIMIT

**Applies to:** 12.1 to 23ai

## Cause

Total PGA across the instance crossed `pga_aggregate_limit` and Oracle killed work to get back under it. Nothing failed to allocate. The node can have plenty of free memory and this still happens.

`pga_aggregate_target` is a target, and it only governs the sort and hash work areas Oracle can shrink. PL/SQL collections and cursor state it cannot shrink, and before 12.1 nothing bounded them, so a bad workload took the machine into swap. The limit exists to stop that.

Oracle aborts the calls of whoever holds the most untunable memory, then terminates those sessions if that was not enough. `SYS` and background processes are never the victim. A parallel query goes as one unit.

The session that gets the error is usually just the biggest, not the cause. When 300 sessions each hold 100 MB, killing the largest changes nothing.

## Check

Read the alert log entry first. It gives the limit, the usage, and the top consumers at that moment. That list is not kept anywhere else.

Where the instance sits against the limit:

```sql
SELECT   inst_id,
         name,
         ROUND(value/1024/1024/1024, 2) AS gb
FROM     gv$pgastat
WHERE    name IN ('aggregate PGA target parameter',
                  'total PGA allocated',
                  'maximum PGA allocated')
ORDER BY inst_id, name;
```

```sql
SELECT   inst_id,
         name,
         value,
         isdefault
FROM     gv$parameter
WHERE    name IN ('pga_aggregate_limit',
                  'pga_aggregate_target',
                  'processes')
ORDER BY inst_id, name;
```

`isdefault` of `TRUE` on the limit means nobody chose it. Oracle derived it from `pga_aggregate_target`, `processes` and physical memory, so it moves when any of those change. On a box with a big SGA that derived value can land lower than expected.

One process or a crowd, which decides the whole approach:

```sql
SELECT   inst_id,
         COUNT(*) AS processes,
         ROUND(SUM(pga_alloc_mem)/1024/1024/1024, 2) AS total_gb,
         ROUND(MAX(pga_alloc_mem)/1024/1024/1024, 2) AS largest_gb
FROM     gv$process
GROUP BY inst_id
ORDER BY inst_id;
```

If it is a crowd, `gv$process_memory` will show `PL/SQL` spread across all of them, and that is an application problem no parameter will hold.

## Fix

Oracle has already killed the victim, so service is usually back before anyone looks. The decision is whether the limit is too low or the workload is too high.

If the limit was derived and the node has headroom, set it properly. Check free memory at the OS first, because raising it past what the machine can back turns a clean error into swapping or an OOM kill:

```sql
-- illustrative, size from the queries above and from free memory
ALTER SYSTEM SET pga_aggregate_limit = 32G SCOPE=BOTH SID='*';
```

Oracle will not accept a limit below 200 percent of `pga_aggregate_target`, so the two move together. Set them together.

Caution: `pga_aggregate_limit = 0` turns enforcement off and puts you back on 11g behaviour, where the PGA grows until the OS refuses and you get [ORA-04030](ORA-04030.md) or a node under memory pressure instead. It is not a fix.

If it is many sessions each holding untunable memory, the fix is in the code: `LIMIT` on the `BULK COLLECT` loops, close the cursors, fewer concurrent dedicated sessions. If one report is responsible, cap its parallelism.

On RAC the limit is per instance. Work being killed on one node while another sits idle is a service balancing problem, not a limit problem.

## Prevent

- Set `pga_aggregate_limit` explicitly. Leaving it derived means it moves when `processes` or the SGA changes, and it moves quietly.
- Alert on `maximum PGA allocated` approaching the limit. The error is the outcome, not the warning.
- SGA plus PGA limit plus OS overhead has to fit in physical memory. Oracle will honour both numbers even if their sum does not fit.
- Use the Resource Manager `session_pga_limit` directive to cap one session, rather than letting a single report threaten the instance.
