# ORA-04031: unable to allocate bytes of shared memory

**Applies to:** 11g to 23ai

## Cause

A process asked for memory from the SGA and no contiguous chunk of the required size was free. The message names the pool involved, usually the shared pool, sometimes the large pool or java pool.

The shared pool holds parsed SQL, PL/SQL and dictionary information. It fills for one of two reasons: the pool is genuinely too small for the workload, or it is being fragmented by large volumes of unshared SQL. Literal values in statements instead of bind variables are the common cause of the second, because every literal produces a new, separately parsed statement.

On RAC each instance has its own SGA. The error is local to the instance that raised it, and the pool that is short may differ between instances.

## Check

Free memory and the largest free chunk per pool, all instances:

```sql
SELECT   inst_id, pool, name,
         ROUND(bytes/1024/1024, 1) AS mb
FROM     gv$sgastat
WHERE    name = 'free memory'
ORDER BY inst_id, pool;
```

Shared pool free versus total, and whether it is being trimmed by automatic memory management:

```sql
SELECT   inst_id, component,
         ROUND(current_size/1024/1024)  AS current_mb,
         ROUND(min_size/1024/1024)      AS min_mb,
         ROUND(max_size/1024/1024)      AS max_mb,
         last_oper_type
FROM     gv$sga_dynamic_components
WHERE    component IN ('shared pool', 'large pool', 'java pool')
ORDER BY inst_id, component;
```

Frequent resize operations in `last_oper_type` indicate the pool is being shrunk and grown repeatedly, a sign of memory pressure.

Statements not being shared because of literals. A high count of near-identical statements is the signature:

```sql
SELECT   sql_text, COUNT(*) AS versions
FROM     gv$sql
GROUP BY sql_text
HAVING   COUNT(*) > 20
ORDER BY versions DESC
FETCH FIRST 20 ROWS ONLY;
```

Alternatively, statements differing only in literal values:

```sql
SELECT   force_matching_signature, COUNT(*) AS stmts
FROM     gv$sql
WHERE    force_matching_signature <> 0
GROUP BY force_matching_signature
HAVING   COUNT(*) > 50
ORDER BY stmts DESC
FETCH FIRST 20 ROWS ONLY;
```

## Fix

To restore service immediately, flush the shared pool. This clears parsed statements and frees the fragmented space:

```sql
ALTER SYSTEM FLUSH SHARED_POOL;
```

Caution: this discards all cached execution plans. Every statement hard-parses on its next execution, causing a short spike in CPU and parse time. It relieves the symptom; it does not fix the cause.

Where the pool is genuinely undersized, raise the floor so automatic shared memory management cannot shrink it below a workable size. `shared_pool_size` is a floor inside the total SGA, not the whole SGA; on a production instance the SGA is commonly tens to hundreds of GB and the shared pool a few GB of that. Read the current values before changing anything:

```sql
SELECT inst_id, name, ROUND(value/1024/1024/1024, 2) AS gb
FROM   gv$parameter
WHERE  name IN ('shared_pool_size', 'sga_target', 'sga_max_size', 'memory_target')
ORDER  BY inst_id, name;
```

Then set the floor relative to the current value, not as a fixed number:

```sql
-- illustrative floor; size to the instance based on the query above
ALTER SYSTEM SET shared_pool_size = 8G SCOPE=BOTH SID='*';
```

The permanent fix for literal-driven fragmentation is bind variables in the application. Where the application cannot be changed quickly, `cursor_sharing = FORCE` makes Oracle substitute binds for literals:

```sql
ALTER SYSTEM SET cursor_sharing = FORCE SCOPE=BOTH SID='*';
```

Caution: `cursor_sharing = FORCE` can change execution plans and affect performance. Test it before applying in production. The correct long-term fix remains bind variables in the code.

## Prevent

- Use bind variables in application code. This is the single most effective prevention.
- Size the shared pool for the workload and set a floor under it so ASMM cannot starve it.
- Watch for repeated resize operations in `gv$sga_dynamic_components` as an early warning.
- Pin large, frequently used PL/SQL packages in the shared pool with `DBMS_SHARED_POOL.KEEP` so they are not aged out.
- Review new applications for literal SQL before they reach production.

## Version notes

- Automatic shared memory management (`sga_target`) applies from 10g, automatic memory management (`memory_target`) from 11g.
- `force_matching_signature` is available from 10g onwards.
